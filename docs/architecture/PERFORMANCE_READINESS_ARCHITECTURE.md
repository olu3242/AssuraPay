# Performance Readiness Architecture

`@assurapay/performance-readiness` completes Wave 3 (Performance Blueprint, Engines 21–30) by adding the measurement and gating layer that sits on top of a Batch 5 blueprint's milestones and deliverables: acceptance criteria, weighted success metrics, dependency tracking, a contractual payment-trigger rule, and a locked performance baseline. As with every prior batch, cross-package references (`deliverableId`, `milestoneId`, `blueprintId`, `requiredDodPackageId`) are held as opaque ids only — this package does not import Batch 5 types or re-validate their existence.

Acceptance criteria attach a measurable tolerance rule, test method, validator role and bounded retest configuration to a deliverable, and become immutable on confirmation. Success metrics are weighted per milestone; confirming a metric is rejected once the milestone's already-confirmed weight would exceed 100%. Dependencies are workspace-scoped blockers with a `criticality` of `BLOCKING` surfaced through a dedicated query rather than embedded in milestone state. The payment-trigger rule (Engine 29) is a **distinct aggregate from `packages/governance-core`'s execution-time `PaymentTriggerEngine`** (labelled "Payment Trigger (10)" in the engine-to-code map from an earlier, execution-lifecycle-oriented prototype) — Engine 29 defines the contractual rule and evaluates eligibility as a pure function against externally supplied evidence (DoD-published flag, accepted criterion ids, blocking-dependency count); it never authorizes or moves money itself.

A performance baseline is set exactly once per milestone and is never mutated; every subsequent measurement is an append-only `BaselineVariance` record computed against that fixed baseline, preserving a full planned-versus-actual history rather than overwriting a single "current variance" figure.

The in-memory `TrustPersistence` adapter certifies orchestration only. Live PostgreSQL RLS and the append-only mutation contract for `acceptance_criteria`, `success_metrics`, `payment_trigger_rules` and `performance_baselines` — whose in-memory equivalents mutate status in place — remain deployment gates, consistent with prior batches.
