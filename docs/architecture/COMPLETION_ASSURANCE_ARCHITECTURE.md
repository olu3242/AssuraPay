# Completion Assurance Architecture

`@assurapay/completion-assurance` closes Wave 4 (Execution Assurance, Engines 31–40) by turning a Batch 7 work item's field verification, issue resolution, change control and acceptance record into a governed completion certificate. As with every prior batch, cross-package references (`workItemId`, `milestoneId`, `blueprintId`) are held as opaque ids only.

Inspection (Engine 36) requires every checklist item to carry a finding before it can complete, and passes only when every item marked `required` resolved `PASS`; a reinspection may only be scheduled against a prior inspection that completed and failed. Issues (Engine 37) route `OPEN → ESCALATED/CAPA_IN_PROGRESS → RESOLVED → CLOSED`, and resolution is only reachable once a linked corrective action plan has been completed and independently verified — a `blockers` query surfaces any still-open `HIGH`/`CRITICAL` issue for a work item. Change control (Engine 38) enforces `DRAFT → SUBMITTED → APPROVED/REJECTED → IMPLEMENTED`, with a decision rationale mandatory. Acceptance decisions (Engine 39) are superseding, not mutating — deciding again for the same work item marks the prior decision `SUPERSEDED` and links it via `supersedesId`, so the full acceptance history is retained.

Completion certification (Engine 40) is the capstone gate: issuing a certificate requires the quality gate to have passed, the inspection to have passed, zero open blocking issues, and an `ACTIVE` acceptance decision whose kind is one of `FULL`/`PARTIAL`/`CONDITIONAL`/`PROVISIONAL` — never `REJECTED` or `DEFERRED`. At most one `CERTIFIED` certificate can exist per work item at a time; revocation requires a reason and is itself never silent. **Engine 40 is a distinct aggregate from `packages/governance-core`'s `CertificationEngine`** (labelled "Certification (09)" in the engine-to-code map from an earlier, pre-catalog prototype built around DoD-evaluation approval rather than the inspection/issue/change/acceptance gate chain here) — the same naming note already recorded for Engines 24, 25, 29 and 31.

The in-memory `TrustPersistence` adapter certifies orchestration only. Live PostgreSQL RLS and the append-only mutation contract for the multi-transition `issue_records`/`corrective_action_plans` tables — whose in-memory equivalents mutate status in place across several steps — remain deployment gates, consistent with prior batches.
