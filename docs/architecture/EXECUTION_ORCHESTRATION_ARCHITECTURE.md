# Execution Orchestration Architecture

`@assurapay/execution-orchestration` opens the first half of Wave 4 (Execution Assurance, Engines 31–40) by turning a Batch 5 blueprint milestone into a governed execution workspace: exactly one workspace per milestone, an assign/transition work-item lifecycle, and the evidence, testing and quality gates a work item must clear before progress can be declared financially earned. As with every prior batch, cross-package references (`blueprintId`, `milestoneId`, `deliverableId`, `acceptanceCriterionId`) are held as opaque ids only.

Work items follow a strict `ASSIGNED → IN_PROGRESS → SUBMITTED` lifecycle (with `CANCELLED` reachable from either open state), and an execution workspace cannot submit while any work item is still open. Progress (Engine 32) is a five-stage ladder — `DECLARED → EVIDENCED → VALIDATED → ACCEPTED → FINANCIALLY_EARNED` — recorded as an append-only series of records per work item; neither the stage nor the percent-complete of a new record may regress behind the most recently recorded one, and `FINANCIALLY_EARNED` is reachable only from a prior `ACCEPTED` record at 100% with a positive earned value. Evidence packages (Engine 33) cannot submit until every requirement marked `mandatory` for the deliverable is covered by a file referencing that requirement's id. Validation (Engine 34) requires notes on a `CONDITIONAL_PASS` and a retest may only reference a prior `FAIL` or `CONDITIONAL_PASS` test. The quality gate (Engine 35) fails whenever a work item carries any open (`OPEN` or `IN_REWORK`) `CRITICAL` defect, and a defect cannot resolve without an assigned root cause.

**Engine 31 ("Execution Orchestration") is a distinct aggregate from `packages/governance-core`'s `ExecutionEngine`** (labelled "Execution (06)" in the engine-to-code map from an earlier, pre-catalog prototype) — the same naming note already recorded for Engine 24 vs. `MilestoneEngine`, Engine 25 vs. `DefinitionOfDoneEngine`, and Engine 29 vs. `PaymentTriggerEngine`.

The in-memory `TrustPersistence` adapter certifies orchestration only. Live PostgreSQL RLS, real object storage and malware scanning for evidence files, and the append-only mutation contract for status-mutating tables remain deployment gates, consistent with prior batches.
