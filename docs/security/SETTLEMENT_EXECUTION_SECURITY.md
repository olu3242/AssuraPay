# Settlement Execution Security

Every record is workspace-scoped and backed by RLS contracts. Financial authorization enforces segregation of duties in code — a requester can never approve their own request — and rejects a duplicate approver outright; authorization is reached only once the threshold-configured number of distinct approvers has signed off. Payment execution (Engine 47) never asserts submission or settlement itself: `submit` and `refreshStatus` require the caller-supplied `PaymentProviderGateway`, and a payment instruction's status only ever reflects what that gateway reports — a provider rejection is recorded as `FAILED`, never silently treated as success. `issue` is idempotent on `idempotencyKey`, so a retried release can never double-instruct the provider. Ledger entries are immutable from creation, and reconciliation exceptions are recorded, never corrected in place. Raising a dispute immediately and atomically freezes the associated release request via an active hold that only the dispute's own closure can lift. A final settlement account cannot close with a positive outstanding balance or an unresolved open dispute, and at most one closure certificate can be issued per account. No method in `packages/settlement-execution` holds, pools, or has signing authority over funds; see `settlement-execution.non-custody.test.ts` for the enforced constraint.
