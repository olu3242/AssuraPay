# Settlement Execution Architecture

`@assurapay/settlement-execution` closes Wave 5 (Settlement Assurance, Engines 41–50) by turning a Batch 9 condition-met release request into an authorized, non-custodially executed, reconciled and finally closed settlement: `Financial Approval & Authority (46) → Payment Execution & Treasury Integration (47) → Reconciliation & Financial Ledger (48) → Dispute, Claim & Appeal Resolution (49) → Final Settlement & Financial Closure (50)`, completing the canonical chain from `CLAUDE.md` through settlement. As with Batch 9, `releaseRequestId`, `paymentInstructionId` and `milestoneId` remain opaque cross-package ids.

Financial approval (Engine 46) is threshold-driven: an authorization can only be requested against a configured `ApprovalThreshold` for the amount and currency, and enforces two independent controls no amount of process discipline should be able to route around in code — **segregation of duties** (the requester can never approve their own request) and **no duplicate approver** (the same approver cannot count twice toward the required approval count). An authorization only reaches `AUTHORIZED` once the configured number of *distinct* approvers has signed off.

**Engine 47 is the second, and most sensitive, custody boundary in the platform** (the first is Engine 44's `EscrowFundingAssuranceEngine`). `issue` requires externally supplied evidence that Engine 46 authorized the request; it is idempotent on `idempotencyKey`, so retrying a release can never double-instruct the provider. `submit` and `refreshStatus` are the only methods that touch money state, and both require the caller-supplied `PaymentProviderGateway` — a payment instruction can never reach `SUBMITTED` or `SETTLED` without the provider itself reporting it, and a provider rejection is recorded as `FAILED` rather than silently retried. `reverse` only records a reversal the provider has already reported; it does not itself reverse anything. See `packages/settlement-execution/src/settlement-execution.non-custody.test.ts` for the dedicated non-custody constraint suite required by `CLAUDE.md` for any PR touching money-movement logic.

Reconciliation (Engine 48) is a pure append-and-compare model: ledger entries are immutable from the moment they're recorded, and a reconciliation record's `matched` flag is computed once from an exact amount comparison against the provider's own statement — a mismatch is recorded as an `AMOUNT_MISMATCH` exception, never corrected in place. Dispute resolution (Engine 49) directly implements `CLAUDE.md`'s "Dispute Trigger... Freezes pending releases the moment a dispute is raised": raising a dispute atomically creates an active `DisputeHold` against the release request, and `isHeld` is the query every downstream gate should consult; the hold only lifts when the dispute is closed. Final settlement (Engine 50) refuses to close an account with any positive outstanding balance or unresolved open dispute (`noOpenDisputes` is externally supplied evidence, following the same convention as Engine 41's trigger evaluation), and issues at most one closure certificate per account.

The in-memory `TrustPersistence` adapter and `deterministicPaymentGateway` certify orchestration only. Live PostgreSQL RLS and a production `PaymentProviderGateway` backed by a real licensed Financial Provider's treasury/disbursement API remain deployment gates, consistent with prior batches.
